# 扫描和 OpenCode 的中间文件生命周期

## 导致磁盘增长的路径

原先 `archive_audit()` 遍历 review、diagnostics 和 git_diff，把按调用生成的文件写入内容寻址目录，再用审计索引引用。SHA-256 可以合并相同字节，每项带独立变量身份的提示词、执行快照与请求仍会生成新对象。同时，收据校验和恢复还要打开 review 下的工作路径，归档后只能继续保存两份。静态提取也把已进入 TU 缓存的工作响应保留到合并以后，部分 OpenCode 私有依赖目录跨批次留下。

归档源码、审计索引和复核原件共用同一个按摘要校验、写透并原子发布的对象存储。现在审计入口只接收明确的扫描证明和固定 Git 输入。逐项复核事件绑定实际原件，Studio、继续复核和导出通过事件、摘要和已验证的历史索引取得内容。正常运行无需遍历整个扫描目录判断单变量能否释放。人工签署仍经过原有 reviews.db 事务和历史事件链。

扫描审计清单包括 scan_state.json、input_manifest.json、input_closure.json、run.json、doctor.json、result_validity.json、storage.json，以及存在时的初始化错误、配置错误、完成证明和独立全量核对证明。Git 差异按固定身份加入基准事实、基准摘要和补丁。派生多核扫描按 scan.db 中记录的组件序号与摘要加入各组件配置及 ELF。模型的 Prompt、Packet 和流输出由具体复核事件登记，扫描审计清单无需逐项复制它们。

## 数据由谁保存

| 产物 | 最后一次使用和清理条件 | 保留的数据 |
| --- | --- | --- |
| 依赖预检查请求、响应 | 父进程读出 Clang 的输入集及签名后释放，冻结输入与实时输入分别做校验 | 预检查结论、编译计划、源文件变更证明 |
| TU 的提取请求、事实元数据、原始响应 | 子进程返回后释放请求。元数据进入合并器后释放。缓存提交并通过校验的 TU 直接从缓存参与合并。工作名释放后才按既定策略压缩单链接缓存。遇到外部占用时记录精确工作文件身份，继续从已提交缓存完成合并。无缓存的响应保持到最后一次合并读取 | 恢复依赖的 TU 缓存、输入快照、最终静态事实。真实生成头文件、CMake 构建输入和编译目录由构建系统管理 |
| 补充提取、独立全量对照 | 补充事实交给调用者、对照数据完成比较后释放。失败诊断保留 | 完整比较证明、固定的 Git Diff 基准和当前侧证据 |
| 每项模型输入、JSONL、stderr、修正答复 | 工作名称绑定变量与本轮调用。写入可重放收据，按 SHA-256 校验原件，原子提交 SQLite 事件与水位，随后释放该项工作副本 | 可从事件找回的原始提示词、Packet、原始答复、错误输出、判定与校验链 |
| 单变量 execution.json 与暂存 result.json | 通过身份与内容校验、对应事件提交后释放。历史执行日志包含独有字段时保留 | reviews.db 的已提交事件、可验证收据、技术失败诊断 |
| 共用案例、工程证据及导航 | 同一批并发调用共用。全部使用者离开后释放共享副本 | 复核实际使用的共用原件按内容只归档一次，静态导航可从 scan.db 生成。退役时按签发格式逐字节比对，保留有额外字段或人工编辑的导航文件 |
| 显式手动备包 | prepare_packets 生成可直接使用的文件。尚未调用模型时保留工作输出，结果包导出按账本的明确清单读取和校验 | 当前手动包、内容哈希、导出包内兼容旧 Portable 的审计索引。同一变量再次备包时，先封存即将被替换的已签发内容。接续自动复核后，原手动输出按逐项收据退役。用户编辑过的不同内容保留 |
| OpenCode 应用缓存和依赖 | 当前批次和会话维护进程退出后，按私有目录身份释放。活动租约阻止其他任务回收 | 指定的会话库、WAL、登录凭据、维护诊断及会话所有权记录 |

默认 SQLite 扫描在单变量提交后即执行清理。已签发的 v1 终态收据保留在 evidence，reviews.db 保存事务事件。现有 Portable 使用两者交叉验证。此项兼容开销计入下面的权威占用。原始 JSONL、Packet 和 Prompt 不再因这一校验在 review 留副本。旧版 JSON/HTML 工作流没有 SQLite 原件时，仍在原位置保存其唯一收据。明确导出的手动材料、运行失败现场、无法证明归属的文件和有效检查点会继续占用空间。

## 提交与恢复

1. 在当前变量的工作目录中完成调用及答复验证。磁盘上的文件名含变量 ID 和调用身份。
2. 持久写入完整暂存收据，按清单写入不可变内容对象并核对大小、摘要和业务绑定。若进程在完整收据写盘后、改名之前退出，重启以进程创建身份、收据摘要、分发序号和请求身份认领暂存文件，再走同一套收据校验。
3. 在 SQLite FULL 同步事务内比较分发时的事件序号，提交单项结果及快照水位。
4. 对该项核对本地字节和权威原件，删除可释放副本，再继续派发。执行日志记录本轮分发序号、请求、进程创建身份及准确文件名。若变量在先前一轮暂停或其进程已退出，下一次完成该变量时也会提交这次中断的实际诊断，随后退役其已核验副本。在答复解析时主动暂停的用例中，重试前保有 5 个文件，重试完成后全部可按原 SHA-256 从事件归档读取，工作目录的该项残留为 0。Windows 占用或删除失败会报告原因。下次继续复核按已提交事件重试。
5. 归档中断时，从原来的暂存收据补完归档并验证。写入大对象时，复制缓冲区绑定对象摘要与进程创建身份。恢复程序可以发布已经写全且摘要匹配的对象，或在权威对象存在后核实并删除已退出写入者留下的部分副本。已提交的复核从事件及证据对象读取。人工签署和历史事件独立保存。

## 整理已有扫描

在目标数据根的 Studio 打开“数据与共享”中的“空间与清理”。生成预览即可查看具体相对路径、字节数、类别和摘要。隔离后可还原。永久释放前再次检查引用与原件身份。预览到执行之间发生新的复核或人工签署时，应重新生成预览。

整理器核对 scan.db、reviews.db、manifest.json、事务水位、暂存恢复收据和历史索引。旧版有些检查点替换了 manifest 中的当前索引，磁盘上留有仍有效的旧索引。整理器识别这些内容可验证的 v1 索引并保留它们及其依赖。SHA-256 文件名自身不足以证明文件可以删除。用户修改过的工作副本和来源不明的旧 OpenCode 运行目录也会保留。历史 CAS 对象的摘要可由同一数据根中的其他扫描引用，整理器会保留这种跨扫描候选，以及无法孤立验证的多硬链接文件。

## 测量方法

复核试验使用真实的建包、验证、SQLite 提交及归档路径，以可重复的模拟回答替代模型。命令为 `py -3.10 -m scripts.benchmark_review_storage --counts 10 100 1000`。通过 `--workers 4` 或 `--workers 8` 可重复并发试验。每次在独立目录运行，不读取生产账号的模型配置。模型调用前后的业务数量和 DONE 状态有断言。

表中的峰值为采样峰值。脚本在归档边界采样目录逻辑字节，并在首项、末项与最终状态查询 NTFS 的实际文件分配量，按卷和文件身份去除硬链接重复计数。目录本身和卷元数据开销未计入。单变量残留在每一个完成回调内检查。必要证据、结果库及 WAL 的增长均计入扫描目录。

### 实际 OpenCode 和 Studio

已安装的 OpenCode CLI 连接到隔离的本机兼容模型服务。九项真实 CLI 集成场景覆盖单变量、并发、私有与共享会话库、启动失败后重试、暂停后继续，以及 Studio 读回。4 个变量、3 个 worker 的会话清理试验精确删除 4 个本次会话，保留 2 个既有会话，SQLite 从 3,772,416 字节压缩到 282,624 字节。关闭可选会话清理的单变量用例同样释放了私有运行缓存，保留会话数据库。这组测试检验实际进程、文件句柄、协议和数据库行为。答复内容来自确定性本地服务。

4 worker 实际执行 5 项，回收 4,022,272 字节会话库空间。8 worker 实际执行 9 项，首轮回收 6,148,096 字节。加入空闲补偿后的独立复测再次精确删除 9 个会话，会话库从 6,221,824 降到 282,624 字节。两组各保留 2 个历史会话，Studio 均能校验归档原件。

已经成功删除过本任务会话的维护服务如果随后瞬时断连，模型调用结束后会重新校验已提交 DONE、分发身份和具体会话归属，给已登记的失败会话一次空闲重试。持续不可达的服务保留补偿记录。

最终源码另行复跑真实单 worker 和八 worker。八 worker 完成 9 个变量，只清理这 9 个任务会话，保留 2 个既有会话。压缩前后私有会话库实际分配为 6,422,528 和 282,624 字节，Studio 已核实归档证据。

共享数据库用例分别在失败重试和暂停继续后精确删除 3 个和 2 个本任务会话。两组均保留 2 个既有会话，ECRA 未对共享库执行压缩。

在 Windows 上将 ECRA_TEST_OPENCODE_EXE 指向实际 opencode.exe，然后执行 `py -3.10 -m pytest tests/test_review_session_cleanup_live.py` 可重跑真实进程测试。模型服务和会话库由测试夹具单独建立。

真实 Chrome 打开独立 Studio 数据根，导入了完整旧 Portable 结果包，查看归档 OpenCode 原件、访问证据、调用链、源码和人工确认历史。在测试副本签署后重开 Studio，签署仍然可见。另一次真实 Chrome 试验打开本机新扫描的工程概览和变量列表，以 SUSPECT 筛选。初始为 1 个技术失败、2 个待复核。点击“仅重试技术失败”后得到 1 DONE、2 PENDING，再点击“继续复核剩余项”得到 3 DONE。两次均由 Studio 后台任务启动真实 OpenCode，隔离的本机模型服务恰好收到 3 项调用。
