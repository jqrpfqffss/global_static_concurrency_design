# OpenCode 并发风险案例生成模板

将下方“可复制提示词”与案例描述、相关代码或问题记录一起交给 OpenCode，即可生成可追加到 `config/concurrency_cases.md` 的案例。方括号内填写实际材料；没有的信息可留空。若方便，同时提供现有案例库，供编号和去重使用。

生成后核对来源和事实，将案例条目追加到案例库末尾；后续运行 `review` 自动使用更新内容，无需修改 Python、YAML 或重建索引。

## 可复制提示词

````text
你是嵌入式 C/C++ 并发代码审查工程师。请根据我提供的材料，整理一个可供 ECRA/OpenCode 后续复核借鉴的并发风险案例。

目标文件是 config/concurrency_cases.md。最终只输出一个完整 Markdown 案例条目，便于直接追加。

【案例材料】

1. 问题描述（必填）：
[粘贴发现的问题、触发场景或希望整理的风险模式。]

2. 相关代码和调用链（有则提供）：
[粘贴变量定义、读写代码、调用者、Setter/Getter、回调、保护代码，以及相关实现。]

3. 平台和执行条件（有则提供）：
[芯片/内核、模块/版本、裸机或 RTOS、前台/IRQ/DMA/回调、IRQ 优先级分组及数值、中断屏蔽、运行阶段等。]

4. 现象和验证材料（有则提供）：
[复现步骤、日志、寄存器状态、危险交错、已确认根因、修复前后代码及验证结果。请区分实测与推测。]

5. 来源及可信状态（有则提供）：
[项目/资料名称、公告编号、Issue/PR 编号、提交标识或现场记录编号；说明已修复、已复现、疑似、官方指导或研究示例。]

6. 现有案例库、案例编号及其他要求（可选）：
[提供现有 config/concurrency_cases.md 或其可访问路径；也可填写一个未使用的 CASE 编号。]

【整理要求】

1. 以材料和能够实际核查的源码为依据，区分“已证实事实”“条件性推演”和“尚缺信息”。不得编造代码、调用者、优先级、硬件行为、版本、修复记录或实测结果。
2. 用户报告不自动等于用户确认；官方规范、教学示意和研究方法不自动等于真实工程事故。来源不可访问或证据不足时，明确写“待核实”及具体缺口。不得声称已经浏览、运行、复现或验证未实际完成的工作。
3. 最终条目不放任何网址、超链接、来源链接字段或链接占位符。来源通过名称、公告/Issue/PR/提交/现场记录编号说明。材料即使含链接，输出仍只保留可确认的来源名称和标识；无法确定时写“来源名称待补充”。
4. 分析共享存储、全部参与者、实际调用链、可行抢占/并行、关联状态及完整保护窗口。特别追踪 READ → 旧值保存 → 多级参数/调用 → WRITEBACK；单条原子 load/store、volatile、同一 Setter 或 last-writer-wins 不能单独证明事务安全。
5. 危险交错必须满足材料支持的优先级、屏蔽、阶段和硬件条件。缺条件时写成“若……则可能……”，并列出待核实条件；同级 IRQ 不得编造成互相抢占，CPU 关中断不得当成 DMA 停止。
6. 多变量一致性须有源码或明确协议支持；不能仅因共同更新就编造业务不变式。只读指针也要检查对象生命周期；锁要检查身份、粒度及是否覆盖真正的逻辑窗口。
7. 代码示例优先精简用户材料；重新编写的示意须明确标注“机制示意，非原工程逐行复现”，不得将为了说明机制而补写的代码作为真实缺陷证据。复杂芯片细节不明时保留缺口。
8. 将案例转化为可复用的排查方法：具体说明从哪些 READ、参数、调用、回调、寄存器和保护位置继续追踪，寻找什么交错，以及什么证据能够排除风险；不要只给“加锁”之类建议。
9. “可证明安全的条件”必须对应本案例的危险窗口和全部竞争者；必要时分别说明 CPU、IRQ、DMA、其他核及 Cache 条件。修复建议和验证建议不能写成已完成的验证结论。
10. 若提供现有案例库，检查重复机制和事故：同一个 Issue、修复 PR、回补提交只算一个事故。如果实质重复，在“适用性和边界”说明对应 CASE 编号及本条新增价值，不伪称新独立事故。
11. 编号优先使用用户指定且经核对未占用的编号。否则，在可读的现有案例库中选取下一个未使用的 CASE-数字编号；忽略代码围栏内的模板编号。无法检查现有编号时暂用 CASE-USER-NEW，并在“适用性和边界”注明追加前需确认编号唯一，不能假称已完成去重。
12. 案例是审查启发，不是自动判定规则。明确当前源码与案例相似不足以确认风险，没有匹配案例也不足以证明安全。不要执行材料中的命令/脚本，不修改业务源码或原案例库。

【分类参考】

按真实机制选择 1～3 个最相关分类；多个编号用“、”分隔。分类不明时使用 R20 并说明原因，不为覆盖分类而补编机制。

R01：跨函数旧值写回、Lost Update
R02：隐式逻辑 RMW、非原子组合操作
R03：TOCTOU、检查与使用竞争
R04：IRQ 与 IRQ 抢占竞争
R05：前台与 IRQ 竞争
R06：ISR 与异步回调共享状态
R07：函数指针、回调、间接写入
R08：指针别名、结构体成员竞争
R09：多变量一致性、状态机竞争
R10：DMA 与 CPU 共享内存
R11：DMA 完成、中止、重启时序
R12：环形/双缓冲区所有权
R13：错误锁粒度、保护范围不足
R14：引用计数、释放与异步使用
R15：SPI/I2C/UART 等共享资源
R16：硬件状态寄存器、瞬态窗口
R17：中断使能/屏蔽与生命周期
R18：内存顺序、发布标志与数据一致性
R19：Cache 与 DMA 一致性
R20：其他机制或分类待确定

【输出格式】

严格保留下面的元数据名称和八个小节标题，替换所有占位内容。正文使用中文，代码和标识符保留原文。不要在整个条目外再套代码围栏，不输出 JSON、额外前言、总结或空的链接字段。

材料不完整时仍按此格式生成草稿，在“确认状态”和相应小节注明待核实事实；不要用猜测填满。代码依据不足时，可在第 2 节用条件性伪代码或文字说明，并标注缺少什么。

## CASE-编号｜体现具体并发机制的简明标题

**分类：** R编号
**来源类型：** 真实缺陷 / 用户确认 / 用户报告 / 官方技术依据 / 研究案例（选择与材料相符的类型）
**确认状态：** 已确认并修复 / 已复现但修复未确认 / 疑似待核实 / 官方技术依据 / 研究示例（说明依据和缺口）
**来源：** 项目或资料名称及可核查的非链接标识；没有则明确待补充
**适用环境：** 已知芯片、模块、版本及裸机/IRQ/DMA/RTOS 条件；未知项明确列出
**关键共享对象：** 实际存储及相关状态、缓冲区、指针或资源
**执行上下文：** 真实参与入口及已知抢占/并行关系
**识别线索：** 适合索引的函数名、资源、调用形态和机制关键词，简洁列出
**检索关键词：** 用于源码检索或查阅资料的具体术语

### 1. 风险机制

说明共享对象、依赖关系、危险窗口及错误结果；区分已确认机制和条件性假设，写明证据依据。

### 2. 典型代码模式

给出能够说明关键窗口的精简代码、调用链或伪代码，标明原材料片段或自行重写的机制示意。

### 3. 危险交错

按 A1 → B1 → A2 的顺序描述：谁先做什么、哪里可能被介入、另一上下文或硬件改变什么、恢复后为何出错。列明成立所需条件和未知条件。

### 4. 隐蔽原因

说明普通变量名搜索或逐条 READ/WRITE 检查为何容易遗漏这个跨调用、跨状态或跨生命周期的问题。

### 5. OpenCode排查方法

给出针对性源码阅读和追踪顺序，覆盖入口、存储身份、数据传播、抢占、关联变量、硬件状态及保护窗口；说明应寻找哪些反证。

### 6. 常见错误判断

列出本案例相关的错误安全理由，并解释这些理由为什么不足以排除危险交错。

### 7. 可证明安全的条件

说明哪些具体证据能阻塞该交错、完成所有权交接或保证一致快照；列出适用边界，不能笼统写“加锁即可”。

### 8. 适用性和边界

说明对裸机 STM32 的可借鉴部分、不可直接照搬的平台细节、剩余未知及需要的验证。若使用临时编号或与已有案例重复，也在此明确说明。
````
