## 4. 内存/扫描：有界流水线、全局求解与可靠恢复

### 4.1 有界 TU 解析

保留原实参、宏、路径、头文件闭包及成功/部分/失败语义；不同 Worker 在**独立进程**执行 Clang 提取，建立有界 in-flight 队列和单写入者/批量事务。TU 的事实在完成验证后立即落盘并发出提交确认，及时释放 AST、响应大对象、进程与文件句柄。数据库写入慢时背压，不因任务持续提交而无限涨内存。保留严格的输入变化门禁和失败 TU 证据，不把局部成功当作整轮成功。

### 4.2 全局求解不是一次性重新加载

当前 `facts = merge(parts)`、`report = analyze(facts, ...)`、`generate(...)` 等路径需具体测峰值，着重处理 giant Python dict/list、重复字符串/函数实例/边、`deepcopy`、全量 `json.dumps`、完整报告计划、跨产物重复索引以及 points-to 工作集。采用稳定整数 ID、关系型映射/紧凑数组、共享只读节点、必要的外存索引、有界缓存及等价的增量不动点工作队列。不能“前半程流式落盘，后半程再次把 50GB 数据全部装进内存”。若外存求解代价过高，应提出分阶段可测替代实现，并维持完整语义，不可暗中降低求解覆盖。

### 4.3 资源管理

提供自动、低内存、高性能三种预设，默认自动；显示用户选择的最大内存预算（建议 32GB 电脑先采用 12GB 常规目标、16GB 峰值目标，**不是既成能力**），允许手动调整。Windows 同时测系统可用 RAM、进程树 RSS、主进程 Private Bytes/Commit、工作盘空闲与临时文件增长。软阈值降低新 Worker 启动/缓存容量，硬阈值尝试安全检查点与停止，不得杀掉别的进程，不能继续到系统崩溃后只抛 `MemoryError`。

## 5. 唯一权威存储、保留规则与数据库效率

### 5.1 总体实现

SQLite 为**权威结构化事实库**，必要的体积很大的低频证据以内容寻址（SHA-256）压缩对象存储；SQLite 保存 ID、关系与对象引用，按需解压读取。不得安装或依赖 MySQL/PostgreSQL 服务，不能把所有 JSON 原封不动存为数据库大字段就宣称已优化。变量、访问点、函数、调用边、points-to、上下文、IRQ/NVIC、保护窗口、初始化证明、覆盖缺口、冲突与多字段一致性存为可查询关系。来源不同的同名 static、同源不同实例、不同条件宏与中断配置必须独立。证据去重须保留类型、顺序与重复次数，哈希冲突不能误合并。

Schema 至少覆盖 `projects/profiles/scans/build_inputs/translation_units/input_dependencies/symbols/members/arrays/functions/accesses/call_edges/points_to/context_bindings/irq_priorities/protection_events/initialization_evidence/coverage_gaps/findings/finding_evidence/diff_impacts/evidence_refs/evidence_blobs/review_receipts`，根据实际分析粒度增加表。字段与关系必须有规范文档和索引计划；查询 `symbol_id → 全部相关证据` 不能临时全库顺序扫描。OpenCode 和 UI 使用同一个 `EvidenceProvider`/`QueryService`，不在各模块再拷贝全量 facts。

### 5.2 证据保留矩阵

**必须永久留存于标准完整结果**：完整规范变量与字段身份、全部与其相关的原始访问事实、完整调用边/路径可重构关系、指针/别名、不动点结论、真实执行域、NVIC、保护、初始化、DMA/多核相关已建模语义、相关未知与覆盖、静态分类、Diff 输入/选择理由、源文件/编译输入指纹、OpenCode 校验后的最终结论与引用证明、技术复核收据、人工事件及历史、版本与完整性摘要。只有 UI 不显示、AI 当前未引用，不构成可删除理由。

**可安全回收**：经过入库和校验的临时 AST/Worker 原始缓冲、完全可从权威库重建的重复大 JSON/MD/HTML、被证据引用计数证明不可达的临时对象、过期但不属于必要审计的格式修复临时 stdout 等。当前复核仍依赖的 Prompt/Packet/证据导航不得提前删除；历史扫描引用的对象不能被清理。可显式选择“标准完整归档/审计归档/精简分享”，精简分享必须标明哪些能力不可用，不得冒充完整包。

### 5.3 SQLite 事务及归档

扫描使用受控批量事务、必要复合索引与短只读连接；管理 WAL/Checkpoint 与文件空间，测量 WAL、数据库和压缩对象总物理大小。用户导出前使用 SQLite 一致快照/Backup API 或 `VACUUM INTO`（资源允许且校验通过时），执行 `integrity_check`、外键及对象哈希/引用/逻辑语义摘要检查。不能复制仍在写入的 db 文件而漏掉 WAL；不能默认关闭安全同步选项换速度。回收采用引用可达性，先预览空间、支持退出/失败回滚，不误删除历史。

### 5.4 原数据导入

支持原 `<firmware>/.ecra` 及现有 `<tool>/workspace` 的实际格式和共享 JSON 封装；**流式**读取大型 facts/JSON/SQLite/复核与历史数据，按 schema 版本无损映射；旧 HTML 有资料但不是无损事实唯一来源。旧数据标识不足时标记 `LEGACY_READ_ONLY/UNVERIFIED`，不得补造可信变量身份。必须先备份、检查所需磁盘、导入、完整字段/引用校验成功，才允许用户自行发起旧文件清理，不能迁移时自动删。旧数据必须独立于扫描目标仓库。

## 6. 数据根、工程配置与 Portable 稳定性

新的目录建议如下，允许保留现有 `WorkspaceResolver` 内部身份规则并做合理调整：

```text
<ECRA_DATA_ROOT>/                          # 默认用户可写数据目录，不在固件、不在会被覆盖的安装目录
  settings/                               # 全局 UI 设置与项目登记
  projects/<project_id>/profiles/          # 每项目/构建变体配置：semantics.yaml + 关联案例/背景
  scans/<scan_id>/scan.db                  # 不可变、已验证的静态事实快照
  scans/<scan_id>/reviews.db               # OpenCode 终态、人工确认事件与当前视图
  scans/<scan_id>/evidence/<sha256>        # 可寻址完整证据
  scans/<scan_id>/manifest.json            # 版本、输入、来源和完整性
  work/<task_id>/                          # 本次任务 Worker、WAL、可恢复状态、日志
  cache/tu/ cache/git/                     # 内容身份校验缓存
  exports/                                 # 用户主动生成的便携结果包
```

工程路径、实际分析 root、隔离 Git worktree、数据目录、真实构建工具与编译输入有清晰来源归属，沿用当前对 Junction/符号链接越界、Git 路径长度、中文/空格/跨盘符、构建文件身份和 `include_uncommitted` 的严谨处理。默认 GUI 多项目配置应保存独立 profile，切换工程不来回覆盖唯一 `config/semantics.yaml`；CLI 仍支持既有单配置入口与 `--config`。GUI 必须能读写项目 profile 的**所有已支持语义字段**，普通选项用表单，高级选项用 YAML，但高级字段不可因 UI 保存而丢失或悄悄重置；配置修改须校验并原子发布。

Git Diff 必须保持当前 `base_ref`→`current_ref` 直接比较，HEAD 固定提交/未提交选项与既有缓存、保守扩大语义一致。`include_uncommitted: false` 不得因为工程里存在 IDE 文件或历史报告而报“工作区脏”；`true` 必须准确纳入实际被使用的未提交/未跟踪修改及输入闭包，不能粗暴按文件名忽略真实源码。多版本扫描不允许污染或混用原工作树与固定版本工作树。**特别是 `include_uncommitted: true`**：须将已暂存、未暂存、重命名、删除、未跟踪且参与真实输入的字节无损地固定到受控隔离快照/副本；不能为了“固件只读”而漏掉未提交代码，也不能继续在原工作区内产生 ECRA 构建或临时输出。要验证补丁/未跟踪文件/符号链接的完整应用与实际编译输入指纹。

## 7. ECRA Studio **冻结界面结构与设计系统**（不能自由设计）

这是本次对旧提示词的关键强化。要求先依据已有文档和四张样图制成 `docs/rearchitecture/ui/01-product-spec.md`、`02-wireframes.md`、`03-design-tokens.md`、`04-interaction-contract.md`、`05-state-matrix.md`，并让真实 UI 逐项实现。既有样图可作为构图与信息架构参考，但**需以本文件的新增功能和 Web 实现替代旧“Qt + HTML”方案**。若已有样图中某个布局不适用于屏幕，要在 ADR 中记录调整理由，不允许凭个人偏好换成通用 KPI Dashboard。

### 7.1 目标用户与设计理念

首要角色：①扫描操作工程师（不熟悉 YAML/CLI）；②排查工程师（关注变量、调用链、旧值覆盖）；③负责人（关注覆盖、人工确认、修复闭环）；④只拿到结果包的离线审核者。每个角色都有“如何进入、看到什么、采取什么动作、任务如何完成、异常怎么办”的完整设计。

唯一正式首页必须快速回答：**当前是哪个固件和构建版本？结果是否有效？哪些问题需要我处理？上一轮处理到哪儿了？下一步点哪里？** 不能只堆饼图、五颜六色卡片、数据库表结构或内部算法名称。优先展示下一步动作，其次展示细节；专业证据可以深入，但不能删减。

### 7.2 强制布局与导航（桌面优先）

默认在 1366×768 可用，推荐以 1600×900/1600×1000 作主视觉回归；适配 Windows 100%、125%、150%、200% DPI。布局：**左侧固定导航 216–240px；上方 56–64px 的项目/构建版本/扫描批次和结果有效性栏；中部业务区域；必要时右侧证据详情面板**。小屏只允许收起侧栏/详情，不得遮挡主要操作。不要把所有配置做成一个长页面，也不要用多级弹窗完成最常见动作。

左侧一级导航冻结为：`项目概览`、`工程配置`、`扫描任务`、`变量与风险`、`覆盖与诊断`、`OpenCode 复核`、`人工确认`、`历史与对比`、`数据与共享`；设置入口放底部。首屏只有一个强主要按钮，随状态显示“添加工程 / 检查并扫描 / 查看扫描 / 继续人工确认 / 打开当前结果”，其他操作次要化。界面全中文，但函数/变量、IRQ、文件路径、Git ref 保留原始专业标识符。

视觉设计：专业 Windows 工程工作台风格，浅色主内容区、深色/中性侧栏、蓝色主动作，低饱和；禁止随意多色大卡片、渐变背景、过多动画、拥挤表格。风险红、疑似橙、未知中性灰蓝、已证明/确认无风险绿，但**所有状态必须伴随明确中文文字**，颜色不能独立表达风险。统一 8px 间距体系、普通正文 14–16px、表格行高 36–44px、页面内边距 20–28px；源码区等宽字体与单独字号控制。支持浅色默认，暗色模式可后续添加，但不能挤占首版完整性。

### 7.3 **页面一：首页/项目概览**

结构固定为：顶部项目身份和状态带；第一行 4 个关键事实卡（静态疑似、无法判断、当前构建已证明安全、人工待确认）；第二行左右两区（左约 65%：按优先级待处理变量和可执行动作；右约 35%：覆盖缺口与未完成扫描/复核提示）；下方简短“最近扫描与历史变化”和“下一步”。**确认风险、静态 SUSPECT、OpenCode CONFIRMED 和人工确认风险分别有来源标签，不能混作同一数字**。每张卡点击后直接打开相同口径的真实筛选列表，不能出现“数字显示 100，点击只有 80”。零匹配、未扫描、结果损坏、历史只读、输入改变均有独立空/告警状态。首页必须清楚解释不同统计分母（canonical 对象、容器汇总、OUT_OF_BUILD）。

### 7.4 **页面二：工程接入与配置**

首次入口只显示“新建工程”“导入历史结果”“打开示例”；新工程向导固定 4 步、可前进/后退、输入不丢：①选择固件目录/工程名；②真实构建方式、Toolchain、CMake/compile_commands、Debug/Release/核心与目标；③分析范围、include/exclude、main/ISR/任务语义及 Diff 选项；④环境检查、执行计划、ECRA 独立输出位置、扫描模式/可选 OpenCode、启动。

常见项用自然中文字段并内置说明；高级语义独立折叠区和 YAML 原文编辑，保存时不覆盖未知字段和用户注释（无法无损编辑则先备份、明确提示或要求另存）；工程路径不自动修改源码。对于 `include_dirs`/`exclude_dirs` 显示目录树与“只排除变量清单 / 仍参与调用恢复”的说明，避免用户以为排除 Drivers 就完全不解析 HAL。Git Diff 提供分支下拉/可输入 ref、当前 HEAD、是否含未提交、比较方向、固定提交/实际工作区提示，以及真实检查错误修复路径。复用旧构建不符合外置规则时明确阻断并说明隔离构建行为。

配置保存后返回工程概览，不要求反复进入高级 YAML。已接入项目日常从首页一键重扫；用户能通过可见 UI 获知哪份 profile、宏、核心和目标正在生效。

### 7.5 **页面三：扫描任务中心**

顶部：扫描任务身份、工程/分支/构建配置、阶段状态和有效性；中部：阶段步骤（准备、构建、输入快照、TU 解析、全局指针/调用分析、风险分类、持久化校验、可选 AI）、当前阶段进度；右/下方：内存与磁盘实时数值、小型趋势图、可检索日志、失败诊断；底部稳定可见真实操作“开始”“安全停止”“恢复”“重试失败”按状态启用。

阶段进度只能使用真实计数；无可用分母必须显示“正在分析，剩余量未知”，禁止编造整体 92% 或预计完成时间。扫描失败必须显示失败发生在哪个阶段、是否保存 TU、是否仍可查看上一次有效结果、下一步具体操作。UI 暂停/恢复按钮只有真实检查点语义实现并通过故障注入后才可出现；否则明确使用“安全停止/从检查点恢复”。工具内存预算不足时显示当前预算、实际进程树占用、停止原因和可操作配置，不得隐藏错误堆栈的唯一诊断入口。

### 7.6 **页面四：变量与风险——核心工作台**

必须采用**左列表 + 右证据**双栏，推荐左 34–40%、右 60–66%，可拖动分割线；在窄屏可以切换单栏。左侧固定搜索和复合筛选条（静态风险、AI 结论、人工状态、修复状态、文件、函数、IRQ、Diff 变化、覆盖缺口），下方虚拟滚动/服务端分页变量列表，默认展示变量名、静态标签、人工标签、定义位置、重要上下文。右侧打开时首屏按顺序显示：

1. **变量身份和一句话结论**（完整中文，不截断，必要时折行），清晰标注这是静态/AI/人工哪一层；
2. **潜在并发时序**：真实 main/IRQ/DMA 抢占或数据竞争路径，若证据不足显示未知条件，不把假设写成事实；
3. **关键访问列表**：READ/WRITE/RMW、源文件行号、执行上下文与保护；
4. **调用关系图/树**：从 main/ISR/回调进入到目标访问，支持放大、折叠、路径切换、上下游完整边查询；
5. **代码定位**：归档来源的文件/行及必要邻近代码，原固件存在时可在本机 IDE 打开；没有原源码时只能看归档证据并标“原源码不可用”；
6. **NVIC/PRIMASK/BASEPRI/保护/初始化/别名/未知事实**：分组分页或折叠，但不静默删证据；
7. **OpenCode 原始合理化结论/缺少条件/修复建议**；
8. **人工确认按钮与完整历史**。

必须能对 `g_mfcInterface.msgSp` 这样的“前台旧值保存→高优先级 PDO/IRQ 更新→前台旧值写回”场景清晰标出多个真实上下文、关联访问点和成立前提。**任何示意流程都必须显式声明“模型示例”或“根据此证据推断”，绝不把构造时序误称已硬件实测**。大图或数万条边按需查询，显示“总数量 / 已显示数量”和继续加载入口；不能只展示 top N 却宣称完整证据。保存列表过滤、当前变量和详情分栏状态，切换变量后不让用户每次重搜。

Diff 模式继续用同一工作台，不新增 diff_index.html。顶部显示 `base_ref → current_ref` 和完整可比性；列表默认只显示确定影响项和保守扩大项（分别标注），证据对照可展开基准与当前；调用链/保护变化属于复核理由，不以“变量名没变”放行安全。

### 7.7 **页面五：覆盖与诊断**

按根因分类（解析失败、宏/编译输入、头文件、函数指针、回调/硬件/DMA、NVIC 运行时有效性等），每类给出影响对象数、相关性证据、具体文件和实际可执行修复建议；支持查看全 TU/零变量 TU、被排除目录和构建闭包。不能用“解析了 99% 文件”替代变量级覆盖保证。跳转到对应变量工作台后保留返回位置。

### 7.8 **页面六：OpenCode 复核**

默认不会强制启用模型；显示候选数量、DONE/PENDING/TECH_FAILED/NEED_MORE_CONTEXT 等原始与中文状态、复核 Worker、超时/模型、摘要修复次数和失败证据；允许启动全候选、仅失败项、停止后继续。静态扫描结果不变时，不因用户打开复核页面就重新跑 Clang。每项对话或 Packet 必须能访问完整被引用证据，没有源码时按能力边界拒绝重新证明，绝不偷偷使用缺少源码的历史报告冒充完整复核。

### 7.9 **页面七：人工确认工作台（P0，不是后续功能）**

最上方显示待确认/确认有风险/确认无风险/证据不足/需重新确认数量、确认进度、当前过滤范围；默认按“待确认”优先，可“一键继续上次未确认位置”，附可见的分页、变量定位和上次工作时间。主体左侧待办列表、右侧与变量证据工作台共用的完整详情和操作区域。**固定主要操作**：“确认有风险”“确认无风险”“暂无法确认”；可填写说明、确认者、修改理由；`确认无风险` 必须要求填写依据或引用明确证据，不允许无说明批量刷绿。确认后数据库提交成功才反馈“已保存”，同时更新分组数量与列表，不刷新丢位置；Ctrl+Z/撤销生成新的审计事件，不硬删除历史。风险处理进度（待修复/修复中/待验证/已关闭/接受风险）是**独立第二字段**，不得将“接受风险”解释为安全。

多用户/跨电脑同一变量的不同决定，必须进入显式冲突列表，支持查看双方证据、处理者、时间、备注、来源包后人工决策。只有同源证据指纹一致才能合并，否则视为不同扫描或需复核。**即使在其他电脑上离线确认，导回后仍必须可见且不覆盖旧历史**。

### 7.10 **页面八：历史、导入导出与空间管理**

历史列表按工程、核心、构建配置、Git ref、扫描模式、扫描状态、日期检索；每个扫描可“打开结果”“与基准对比”“继续人工确认”“导出标准包”“导出仅人工确认增量”。导入来源包括其他电脑的 `.ecra-report`、确认增量包以及旧 `.ecra`/工具 workspace；必须在 UI 显示校验阶段、文件来源、风险、迁移结果，不要要求用户复制到隐藏目录才能操作。

数据管理展示**真实**扫描库、证据、缓存、Git 工作树、构建、临时、历史/导出各类占用、可安全回收估算及回收理由；只允许明确选择清理，要求二次确认，不得把“移除项目”变成递归删除固件。清理操作要有 dry-run 和错误恢复策略。结果包打开成功后可以独立于原固件源码使用 Viewer 浏览；原固件位置不存在时，UI 须用“归档证据模式”标签说明限制，而不是阻止打开历史结果。

### 7.11 交互细节与易用性验收基线

- 所有页面必须设计 `LOADING / EMPTY / VALID / STALE / PARTIAL / FAILED / OFFLINE_ARCHIVE / PERMISSION_ERROR` 等实际状态；用户不能把数据尚未加载误认为“无风险”。
- 禁止同时出现多个强主操作；禁止把配置表单和复杂代码证据挤在同一主视图。复杂表单为分步骤向导并附解释；危险操作先预览影响和路径。
- 绝不将 UNSAFE/SUSPECT/UNKNOWN 只靠红绿表示；所有标签使用中文+原始术语提示；未来未知 enum 显示“未识别状态：原始值”，不得默认映射 SAFE。
- 输入校验必须指出字段、原因、示例修复；构建工具缺失必须给出具体路径/版本和修复步骤，且不能误称 OpenCode 未配置为静态扫描失败。
- 支持全键盘 Tab 导航、Esc 关闭弹层、Ctrl+F 聚焦变量搜索、复制变量全名和证据引用、合理的焦点回归，Tab 键不能困住详情弹层。
- 在 1366×768、1600×900、1920×1080，100%、125%、150%、200% DPI 真实浏览器截图验收：主按钮、搜索、关键结果状态均无需水平滚动可见；长变量名可复制且完整显示在详情，摘要**不得直接截断语义**；临界区/中断路径图不能因视口裁切而遗漏证据。
- 中文优先，Windows 文件/路径、源码、Git refs 原样显示；不生成一堆英文 `UNKNOWN_PREEMPTION/UNRESOLVED` UI 标签。无法确定中文含义时显示中文解释与原始技术枚举。
- 不需要云账户、不默认上传任何源码、扫描事实或人工确认；导出包含敏感源码时清楚提示。

## 8. 人工确认与跨版本数据模型（不可省略）

静态数据在 `scan.db` 发布后不可变；OpenCode 最终复核独立保存，人工决策在独立 `reviews.db` 事务化保存。不要直接把人工状态写进分析器的 static `findings` 或变更 `SAFE/SUSPECT/UNKNOWN`。推荐人工判定：`PENDING/CONFIRMED_RISK/CONFIRMED_SAFE/NEED_MORE_EVIDENCE/RECHECK_REQUIRED`；处理状态：`TODO/FIXING/TO_VERIFY/CLOSED/ACCEPTED_RISK`，不要混淆两个字段。每个事件包含 `event_id, scan_id, project_id, symbol_id, finding_id(optional), canonical evidence fingerprint, reviewer identity/display name, timestamp UTC, decision, handling_status, comment, revision, source device/export package, predecessor event id`。用户未登录时“确认人”是可编辑声明而不是经过认证的身份；UI 不得伪称已完成身份认证。

每一次改变确认/处理状态都创建事件，当前状态由事件日志有序投影，事件不可悄悄删除或覆盖。支持同一用户分批确认、继续上次位置、确认后筛选列表同步变化；同一个结果包反复导入幂等去重；双电脑离线并发决定需要明确冲突解决，而非 last-write-wins。重新扫描只有可证明完整相关语义无变化时才可继承人工结论并附原确认来源；代码、调用链、上下文、保护、覆盖或构建变体变化时置 `RECHECK_REQUIRED`。静态风险变为“本轮未观察到”不能直接当“已修复”，需核对扫描范围与源码可比性。

## 9. OpenCode 证据读取与旧报告淘汰策略

建立 `EvidenceProvider`/只读证据导航服务，支持变量级所有 accesses、完整 calling graph、物理上下文、保护窗口、NVIC、关联源码位置、覆盖缺口和 Diff 证据。大数据使用分页、cursor、总数、证据哈希与分段范围，不能因 token 上限随意裁剪。给 OpenCode 一个可审核的“索引 + 按需取段”路径：每段可继续读取，直到模型访问到完成本变量判定所需的全部证据；保留当期原始 Prompt 与深度复核八步逻辑、SAVED receipt、FORMAT_FIX、SUMMARY_FIX、TECH_FAILED、review-failed 行为，不改风险推理合同。任何无法读取的证据须明确 `missing_context` 和技术状态，不能默默缺失并输出 CONFIRMED/SAFE。

迁移时为 `checked_scan`, `generate`, `review`, `status`, `report`, `review-failed`, `git_diff`, `safe sample`, `scripts/*.py` 所有旧路径列出完整消费者清单和新 API，逐个通过测试。日常新扫描**不生成旧 HTML/巨型 JSON/MD**；开发验证的旧格式导出须显式受控且不进入最终用户存储清单。保留 OpenCode 技术和推理审计所必需的输入、输出、模型/提示词标识、验证状态与证据指纹，允许回收纯冗余中间格式文件。

## 10. 便携结果包、脱离固件查看与安全

定义 `.ecra-report` 自包含版本化 ZIP64 归档：`manifest.json + 已冻结 scan.db + reviews.db + evidence/<hash> + 数据/schema/输入/引擎/扫描来源/完整性说明`。可以无原固件源码、Git、ARM GCC、Clang、OpenCode、Python/Node 系统安装而在已解压的 ECRA Studio/Viewer Portable 中导入查看归档全部证据和人工确认，并可继续确认然后导出。离线 Viewer/扫描器使用**同一数据协议**，不能再开发一套不兼容导入器。支持 `.ecra-review-delta` 之类只有人工事件的小包，需匹配扫描与权威证据指纹、版本和包来源，重复导入幂等。任何损坏、未知 schema、输入版本不可信的包不得污染已有有效数据或导致原确认丢失。

导出时必须停止对静态库写入，生成 SQLite 一致快照，校验完整对象引用、SHA-256 与 manifest，使用安全压缩和可恢复的临时目录；导入需防 ZIP Slip、压缩炸弹、符号链接、路径穿越、任意 SQLite 外部访问与恶意脚本执行。默认把数据视为**不可信内容**，源代码片段只渲染为文本，不让 Markdown/HTML/代码注释执行本地命令。本地服务只绑定 `127.0.0.1`、随机端口和会话令牌，检查 Origin/Host/CSRF，路径 API 严格仅在受控项目/导入/数据目录内操作；不可暴露任意文件读取或 shell。显式调用工具使用 argv 参数数组和受限命令映射，不拼未经验证的 shell 字符串。

## 12. 专业 UI 质量门禁与自动评审机制

建立 `docs/rearchitecture/ui/06-ux-review-checklist.md`，每页给出：真实用户目标、默认主按钮、入口和返回路径、核心信息层级、全部交互状态、错误文案、键盘/屏幕规格、测试脚本路径、实际截图链接、需人工确认事项。通过 `scripts/validate_ui_contract.py` 或等效测试验证页面路由、所有可点动作对应真实 API、无空实现或假的 `setTimeout` 成功、无硬编码演示结论渗入生产结果、服务端分页可用、状态可追踪。规定截图回归参考既有 `docs/assets/desktop-proposal/` 的四个页面**信息结构**，但实现后的截图以新的冻结线框图为机械对照；有差异必须记录为什么更有利于用户。

只做视觉像素相等不等于可用。需要组合三类测试：①视觉与信息结构检查；②真实操作端到端流程；③业务状态与数据库的一致性。优先修复影响认知的缺陷，例如“复核完成误显示安全”“确认保存实际上没有持久化”“历史包缺证据仍显示已证明安全”，这些比阴影和圆角优先级高。若某关键场景失败，Phase 不得通过。

## 13. 技术和性能验收门禁

**G1 语义等价**：旧/新同源同构建完整事实、符号身份、访问、调用边、points-to、上下文、保护、NVIC、覆盖、findings/安全理由/未知、Diff 选择与影响原因全部逻辑等价；分类差异非 0 即 FAIL，证据差异非 0 且未经语义证明即 FAIL。OpenCode 读取完整证据，格式与结论不退化。

**G2 大工程真实原生扫描**：使用已有 INAV H743 388 TU 工程（获准使用的本地副本），另外 TMFC/H747 真实场景或等价真实工程，再选独立 STM32 工程覆盖 DMA/回调/RTOS；至少三类真实工程，不将已有 JSON 回放、小型 fixture 或模拟数据库称为原生全量验证。代码仓库没有客户固件时不能私自访问，须说明缺失并给可复现脚本。

**G3 内存**：在 32GB Windows 电脑目标常规 ECRA 资源 ≤12GB，峰值目标 ≤16GB，同时记录进程树 RSS、主进程提交、操作系统可用内存和分页；上述目标是工程指标，若因完整全局关系仍超出必须如实列 FAIL/待优化，不准删证据降内存。

**G4 磁盘**：记录扫描期间**磁盘峰值**、最终标准完整归档、WAL、缓存、外部构建/worktree 与共享对象大小；目标相对同输入旧版本最终物理占用降低 ≥70%，实际未达到需列原因与可复现下一步，不能靠删除有效历史/审计对象凑数字。

**G5 健壮性**：异常退出、Worker 崩溃、磁盘满、输入变化、数据库损坏、WAL、过期锁、迁移中断、非法包、不同盘符中文路径全覆盖；最后一次有效扫描必须存在且不可被新失败扫描污染。

**G6 数据一致性**：`scan.db` 全部关键约束、外键、证据哈希/引用、人工事件不可丢、历史兼容、导入导出不变、离线 Viewer 无源码查看同一详情与确认；导出包和源数据库对象集合及逻辑摘要一致。

**G7 UI 完整**：U01–U24 逐项 PASS/FAIL/NOT_VERIFIED；真实 Chromium/Edge 测试结果和截图。关键按钮不能只是页面 mock。无关键阻断缺陷方可发布。

**G8 Portable 离线**：Windows x64 干净机器：新建工程及扫描版本带内置 Python/Clang/工具链；只查看包的模式无需固件与外部分析工具；页面资产不在线请求 CDN、字体、脚本，离线运行；工具升级后旧数据根不被覆盖。

注意：已有 `docs/inav-h743-git-diff-validation.md` 记录过早期事实 JSON 66GB、DB 92GB、进程峰值约 55GiB，以及后续优化的大幅变化；性能对照必须标记具体旧/新引擎、运行环境与输入版本，不能把不同版本测量拼在一起宣称性能收益。

## 14. 完整交付过程：分阶段双门禁

| 阶段 | 必须交付的实际成果 | 进入下一阶段的硬门槛 |
|---|---|---|
| Phase 0 基线 | 代码/数据依赖图、完整 Golden Baseline、模块迁移表、产品线框与交互合同 | 无未解释的关键事实依赖；有黄金对照或明确阻塞 |
| Phase 1 数据根 + 权威库 | 复用 WorkspaceResolver，新数据根、规范化/压缩存储、原子持久化、旧报告消费者清单 | 同输入全字段可恢复；目录外置、旧数据未误删 |
| Phase 2 低内存扫描 | 有界 TU、背压、可恢复状态、全局分析资源优化、原生大型扫描 | G1/G3/G5 实测；不改算法/覆盖；否则保留阶段阻断 |
| Phase 3 OpenCode 迁移 | EvidenceProvider、review/review-failed/status/diff 完整适配，不再生成旧 HTML/巨型派生文件 | 所有已知消费者迁移；完整证据回归 PASS |
| Phase 4 GUI + 人工确认 | 全中文本地 Web，上述全部页面、确认事务/审计、状态联动 | U01–U18、U22 实测与截图；不存在假按钮 |
| Phase 5 导入导出与协作 | `.ecra-report`、确认增量包、旧版迁移、安全/冲突/离线 Viewer | U19–U24、G6/G8 实测、历史不丢 |
| Phase 6 整体验收 | 完整测试与真实 3 项目回归、性能基准、Portable、文档、演示与风险清单 | 所有硬约束 PASS，未验证项目如实标注，不虚报完成 |

任何 Phase 不得通过删测试、降低语义或伪造结果过门禁；如果上一 Phase 未达实测目标而仍能进行互相独立的后续开发，可以继续开发，但最终必须保持明确的 BLOCKED，不能在总结中写“全面完成”。优先让用户真正用起来，再局部迭代细节；不能等全部功能都写完才发现 UI 交互不合理。

## 15. CLI/历史兼容性

原有 `py -3.10 run_ecra.py`、`--scan-mode full|diff`、`review`、`review-failed`、`status`、`doctor`、`report`、`--config`、`--project` 的功能语义尽可能兼容；新增 `ui`、`import/export`、`storage cleanup`、`reviews` 等按现有命令风格设计。允许打印 UI 入口地址、Scan ID 和结果库路径替代旧 HTML 链接，不能因为默认不生成 HTML 就让状态命令或 OpenCode 无法启动。所有结果都从权威库读取，CLI 与 GUI 的分类统计、复核候选和输入验证必须来自同一业务服务，避免双重规则。

用户双击 `ECRA.cmd` 或轻量 Windows 启动器可自动启动本地 Web 服务并在浏览器打开，关闭后不遗留失控后台进程或误杀正在运行的受监督子任务。没有安装 Node 或系统 Python 时 Viewer 仍能离线使用。Portable 的 `build_portable.ps1` 必须包含新后端依赖的离线 wheel 与前端编译产物，严格核对真实 `python310._pth` 和嵌入解释器；不需要额外安装 MySQL 或另一个 Python。可选 OpenCode 仍按现有方式外部连接，不要打包它。
