# 大型项目导出长时间无响应：根因与修复

日期：2026-11-13。全程由 Codex 直接实现和验证，没有调用 OpenCode 或 Claude Code。

后续已进一步优化到约 4 分 12 秒，并完善进度条，见 [大型项目导出提速验收](large-project-export-speed.md)。本文保留首轮根因与验证过程，当前实现以提速报告为准。

## 复现与根因

使用已有的真实 INAV STM32H743 全量扫描归档 `H:/ECRA-NATIVE-L78-SEED0/scans/native-golden`。静态数据库为 **12,590,510,080 字节**，有 **12,172 个变量对象**、**2,665 个证据对象**。这是已扫描结果的交接验收，没有重新扫描固件。

旧版从“数据与共享 → 导出标准完整包”发起一个同步 HTTP 请求，整个校验、快照、压缩完成后才返回下载地址。界面一直占用全局 busy，只显示“正在提交或读取”，无法了解阶段、取消或在刷新后找回操作。

对原实现运行 313.876 秒后，连续每分钟的堆栈采样均停在 `validate_schema()` 的 `PRAGMA integrity_check`；尚未进入压缩。CPU 累计仅 12.969 秒，工作集约 22 MB。该次只读复现由验收程序主动停止，不能当作一次完成导出的总耗时。

代码中还有重复工作：同一静态数据库先在 `validate_schema()` 校验，再在 `EvidenceProvider.validate(deep=True)` 校验，复制快照后又校验一次。首尾两次使用 SQLite 默认的小页缓存，面对多 GB 数据及索引会产生大量磁盘读取。随后默认以 BZIP2 最高等级压缩。大库上的正常长任务因此呈现为“卡死”；本次未发现线程互相等待的死锁。

SQLite 的整库检查还可能长时间停留在单个 VM 指令内，普通的指令计数进度回调不足以保证心跳或及时取消。

## 修复后的行为

- 界面创建后台导出任务后立即释放操作状态；显示真实阶段、耗时，以及快照/压缩阶段的实际进度。
- 任务与下载结果保存在数据目录。刷新页面、切换页面后可继续查询；已完成的包可以重新下载。
- 同一任务重复点击会复用正在运行的任务；同一数据目录限制同时执行一个后台导出，防止叠加大量磁盘与内存开销。
- 默认使用快速 DEFLATE；仍可主动选择省空间 BZIP2，两者包含相同完整证据和记录。
- 先建立一致快照，再对**实际导出的快照**检查结构、完整性、外键、全部证据哈希和查询投影，去掉重复整库校验。导入和 Git 差异归档的基准校验也合并重复检查。
- 压缩采用分块读取和 ZIP64 流式写入；原生浏览器下载保持流式传输，不构造整个文件的 Blob。
- SQLite 校验使用独立心跳线程和线程安全的 `interrupt()`；取消后清理私有临时文件，只有完整包才原子发布。
- 后台任务持有数据活动锁，导出期间不能清理或搬走正在读取的数据。异常与服务重启留下明确状态，不把未完成的包当成成功文件。

完整性校验、全部证据、人工历史和原子发布没有省略；本次也没有修改并发风险分类算法。
