## 首次配置、扫描、停止与恢复

源码服务使用 `py -3.10 run_ecra.py ui --data-root H:/ECRA-quality-20261108/ui-data`，数据根与工具分离。最初误将测试根放安装目录时被正确拒绝，未放宽限制。全新首页入口、教学示例及覆盖边界可见。

实际从工程向导逐项填写工程名称、F030真实固件根、Cortex-M0、已有真实编译数据库；经过四步配置，点击“开始此配置扫描”，由产品保存配置、执行真实预检查后自动扫描。没有从 API 注入配置或任务状态。

- 旧默认生成的数据库配置不探测系统头，预检查通过但最终 4/4 TU 为 FAILED（缺 stdint.h）。原失败扫描 `f2c3ae5a6d7c4a97ba8131e741b89823` 保留，事实见 `output/quality-20261108/ui-initial-db-coverage.json`。预检查验证输入闭包，不是完整 AST 覆盖成功证明。
- Q302修复后重新走全新向导，“从实际编译器探测”默认选中，保存原文明确含 `auto_system_includes:true`；旧保存配置原文不变。
- 新扫描 `5c77d37945d84b87b036c21858c61255` 中实际点击“安全停止”。该次已完成TU提取，在输入验证阶段收到停止；任务为 INTERRUPTED/130，没有冒充完成，没有手工改状态。
- 点击“从已验证TU恢复/重试”，生成新任务/扫描 `4a21300df3e841dea68a93106160c615`，重新校验输入与依赖，实际命中2TU缓存、重新提取2TU、损坏0，随后发布。原中断任务保留。
- 点击“打开扫描结果”，项目名/批次/来源可辨认；15对象，分类13（静态安全7、疑似1、未知5），容器2，人工待办6。2TU完整、2TU部分、0失败，退出2/INCOMPLETE保留。没有把发布完成等同于全工程安全。

主要证据：`11-scan-stop.png`、`12-real-resumed-result.png`、`final-scan-*.txt`、`stopped-snapshot.txt`、`resume-completed.txt`、隔离数据根 `work/tasks/` 与 `scans/`。真实固件未重建，编译数据库适用范围由独立工程记录说明。

## 连续人工确认与关闭后继续

源码教学库实际连续处理 g_counter、g_msgSP：阅读跨IRQ读改写及旧值写回位置，填写明确标测试的确认者/依据，保存后待办6→5→4，静态疑似仍独立。真实写锁导致第二项保存失败，草稿保留；解除锁后重试成功。

关闭服务、关闭整个测试浏览器后，用新启动URL和同一持久浏览器目录重新打开；没有 state-load、恢复 localStorage 或重新注入数据库。概览仍为人工待办4、独立人工风险2。实际服务重开还由[state.md](state.md)核对事件ID与静态hash；独立界面检查者另外完整走通剩余队列和搜索历史，见[independent-ui.md](independent-ui.md)。所有签署仅在隔离教学数据中，不作为真实工程签名。

Q401修复前，1366×768打开填写区后签署动作底边约797px，超出视口。修后底边约745px，填写/保存/失败状态下仍可操作；证据独立滚动，收起填写区恢复更大阅读面积。原/修后截图03/04及只读几何测量保留。

## 便携目录的实际操作

从本轮独立 `H:/ECRA-quality-20261108-delivery/便携 中文/ECRA-Portable/ECRA.cmd` 启动；子进程 PATH 仅有 Windows系统目录，数据根为 `H:/ECRA-quality-20261108/packaged-ui`，没有.git。包内Python3.10.9启动真实服务，浏览器正式URL打开空库→教学示例→人工确认。

使用独立SQLite连接持有真实 BEGIN IMMEDIATE 写锁，再在页面点击保存；不是拦截网络或伪造失败响应。

1. 最终错误状态明确显示“人工确认保存遇到数据库占用”、旧记录保留、草稿保留与核对后重试；HTTP为409/DATABASE_BUSY。截图15是真正等待错误返回后采集，截图14只是在请求中，不能作失败证据。
2. 失败期间原事件数为1，原静态SHA-256为 `261ff9b60b1ce40f233704520d93e280804d07ee1bc119cb5430bd9b67bae12e`。
3. 释放实际锁后再次点击保存，事件数2，静态hash不变，页面保存成功且待办5；截图16。两次故障产生的控制台HTTP错误为预期注入，不是零错误声明。
4. 填理由并实际点击“撤销上次确认”，历史保留3个事件，恢复前一次风险签署，待办仍5。这里撤销的是第二次更正，不是清空全部历史；截图17。

6. 真正关闭浏览器后，以同一持久目录重新打开正式URL，人工待办5、人工风险1保留；点击继续选中g_msgSP。随后关闭服务，再从最终ZIP解压目录启动同一数据根，3事件及静态hash保持、继续队列正常；见[封包后验](postflight.md)。
