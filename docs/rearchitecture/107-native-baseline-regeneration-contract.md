# 原生基准失效后的新权威库合同

在已推送`26e164e`上追加真实原生CMake专项，发现：首次基准成功；下一轮真实CMake刷新改变`CMakeCache.txt`，完整输入门禁正确拒绝旧检查点。原`prepare_base`随后重新分析到同一目录，而`scan_persistence.persist`按不可变权威库合同保留已有`scan.db`，只追加运行时数据，结果新state与旧库不一致。新增完整校验因此拒绝发布，而不是静默使用旧库。原完整重建读法与有界读法对旧库所得摘要相同，问题不是有界算法漏字段。

旧失败不修补指纹；原失败收据/诊断保留。修复应适用于所有正式基准失效（输入/配置/引擎/完整性），不能只对CMake异常放行。

具体实施：沿用`WorkspaceResolver.for_results`及现有`git_diff/artifacts`；完整验证失败后若旧候选目录有数据，分配新的`base-<固定SHA>-<随机ID>`目录执行全量原生分析。旧目录、DB、归档摘要、旧pin均原样保留。一个小型原子索引只在摘要/TU门禁、完整事实归档和patch均完成后更新，下一轮从该索引选候选，随后仍执行全部原门禁，索引本身不构成信任。相对目录名只允许该固定SHA及既定UUID形式，拒绝路径穿越、链接、不同SHA和未知schema；不增加workspace解析器，不递归搬动旧目录，不改变`persist`不可变规则。旧CLI兼容路径保留原行为。

完成的TU继续放在原workspace主缓存下按固定基准SHA隔离的`git-baselines/<SHA>/tu-v1`，沿用原完整输入/配置/引擎/内容键；新结果目录不意味着重做所有已提交TU。不得把不完整的事实库当检查点续算；恢复到全局入口。

验收必须覆盖：真实CMake/ARM外置静态库及独立无缓存全量核对；改变真实编译宏使基准数组大小4→8字节，不能返回旧事实；新基准通过原完整检查点校验，旧库/旧pin字节不变；可证明输入不变的跨批次摘要复用仍通过；未知/越界索引阻断；合并前实际中断后新目录命中2个已提交TU；索引发布前失败不改旧索引/旧库。真实构建缓存变化时不强求缓存命中，完整正确性优先。CMake未提交修改仍未实现，不计此专项。
